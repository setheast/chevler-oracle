## 1. Product master from the Access record

**What:** the Manufacturing Access DB holds 6,659 real products: dims, paper and its mill reel, QPA and waste, routing with run factors, nest / sleeve / pack, outer carton and pallet build, order notes, order history. Oracle's **Products** should hold the full range, searchable, loading into the quote form as a **Draft** to confirm. Nothing should be re-keyed by hand.

**Proved here:**
- 2,015 of 2,026 case and wrap products load into the Cases form.
- 1,665 of them load fully pre-filled.
- Every assumption the loader makes is shown as a plain-English note.

**Port:**
- `server/access-product-map.ts`: template from the forming machine; paper by stock code → mill-reel code → type/colour name table; print type; piece / QPA / mother reel; packing; machine route with strokes/min derived as run factor × 1000 ÷ 60 ÷ nest ÷ heads; single-matching-die fitting.
- `scripts/extract-access-reference.py`: the extract that produces `server/access-extract/*.json`.
- **Treat as admin-editable data in Oracle, not code:**
  - the paper name table (`casesMaterialName`);
  - the template rules.

**Extract fields Oracle needs:**
- `material.motherCode` — the BOM parent; it matches the price list for 1,520 of 1,998 case/wraps.
- `material.printType`
- `packQty` — `STOCK_SO.Sale Qty`.
- `orderNotes` — five note fields on `TblProductCode`; present on 2,638 products.
- `carton` and the pallet build (see §2).

**Not done yet:** sheets, discs, liners and reels → the Main calculator (4,360 sheets). The mapping gap is wider there: only about 140 Access paper codes match Main stock codes.

## 2. Pallet build lives on the outer carton

**Ruling:** the YF855 Access screen showed 6 × 5 = 30 packs per pallet, while the extract had nothing. That exposed where the figures really live (production-knowledge §15).

**Data:**
- **Where the build is held:** the product's carton — the `TblBOM` line with Mat Group "Carton" — carries the pallet build in `TblMaterials` "UK/EU Units/Layer × Layers".
- **What's wrong with the product fields:** `TblProductCode`'s own Units/Layer and Layers are a legacy pair, blank on all but ~140 products.
- **Coverage after the fix:** 3,203 of 6,659 products now have a pallet build (140 product-level, 3,063 via the carton).

**Oracle:**
- **Make CARTON an entity** (code, outer code, flute, colour, W × L × D, UK and EU builds). Products link to it, because one carton serves many products.
- **Pallets per job** = packs ÷ packs per pallet. That's the input the PlasPac per-job delivery costing needs (CLAUDE.md, ERP endgame §9).
- **Remaining gap:** about 3,450 products have no carton build, mostly sheets. Production must supply those; don't re-ask for the whole range.

## 3. Routes are separate from products

**Ruling / design (Seth):** WBIG03 ran on VP-16 from cut sheets but prices far better on 6REEL from a slit reel. In this sandbox **the template is the route**, so moving a job between routes is a manual step (production-knowledge §16 addendum, CLAUDE.md "Price on another route").

**Port:**
- `server/route-move.ts`:
  - `machineRouteLayout` (machine → route);
  - `casesTemplateForMachine`;
  - `PRODUCT_INPUT_KEYS` — what belongs to the **product**, as opposed to the **route**;
  - `moveCasesRoute` — rebuilds the route: former + die, conversion, reel, QPA by rule.
- The route-move record on quotes: `cases.routeMove` (both routes' prices).

**Oracle:** one product, many capable routes. Price every route in the background, compare them side by side, recommend the cheapest, and allow an override that is recorded. This is the founding design's "automatic machine selection". The machine → route mapping and the product/route split of inputs carry straight over.

## 4. Speeds from Access are unverified (calibration)

**Ruling (Seth, 14 Oct 2026):** "the default machine speeds are all wrong from Access". The 168×111×37 6-7REEL die was recorded at 4/min, the same as its VP-16 die. 6REEL and that die are now set to 12 on the live site (production-knowledge §16 addendum).

**Impact:** speed decides route choice. WBIG03's reel route is +11% at 4/min but −30% at 12/min.

**Oracle:**
- **What carries a confidence level:** every speed — imported die rated cycles, work-centre defaults, strokes/min derived from run factors.
- **The levels:** estimate → observed → verified (the founding design's confidence system).
- **What goes in the Calibration module:** a review cadence and a burn-down of speeds that are still unverified.
- **What must not happen:** Access speeds must not be imported as truth.

## 5. Multi-head reel-fed dies cut staggered

**Ruling (Stuart, 14 Oct 2026):** on a two-headed tool the cuts are **staggered**. One slit reel feeds every head, so:
- **piece width = the die's web** — YF855: 263mm for a 133mm blank on 2 heads;
- **QPA = blank ÷ heads ÷ reel metres.**

This supersedes the 10/11 Oct per-lane reading (production-knowledge §16).

**Why it matters:**
- Material weight is the same either way.
- But the per-lane reading halved the **MOQ**, and its piece width wasn't the reel that's actually slit and bought.

**Port:** in `server/estimate-checks.ts`:
- `reelHeads` — heads from the tool, else the machine's no-out setting, else the 8/9 leading-number rule;
- `reelLayout` / `autoQpa` / `blankGuide`;
- the `tool-lane-width` check.

**Oracle:**
- **Dies:** carry heads and the measured web width.
- **Bill of materials:** the reel component is the full web, with QPA divided by heads.

## 6. Oblong slit width comes from the mother reel

**Ruling / evidence (Seth's question, 14 Oct 2026, proved against Access):** slit width = floor(mother ÷ lanes), where lanes = floor(mother ÷ (D1 + 2·D3 + 10mm minimum spare)). It's the same method as round cases (production-knowledge §16 addendum).

**Evidence:**
- **49 of 61** oblong reel-fed products match to 1mm — **86% of their orders** (WBIG12 295, EH990 285, WPAN04 281, EH400 263).
- The exceptions are small old 1REEL cases run at fixed narrower widths.

**Port:** `OBLONG_SLIT_MIN_SPARE_MM` (= 10) in `server/production-rules.ts`, and `blankGuide` in `estimate-checks.ts`.

**Oracle:**
- **The minimum spare:** an admin parameter.
- **The rule:** a routing-step calculation for the slitter.
- **Confirmation:** Stuart's is still pending.

**Evidence:**

## 9. The internal quote is a complete blueprint, in screen order

**Design (Seth):** the internal PDF's Full Workings lists **every field and every guide** in the order the estimator shows them. It covers:
- **Guides:** blank & reel guide, QPA working, speed steer, standard vs used speed, die fitted, die suggestions, tooling and origination workings, layout cards, cheaper configurations, utilisation.
- **Snapshots** of the advisory panels, taken at quote time: similar products, layout, optimiser.
- **The route move**, if there was one.
- **A catch-all**, so no stored input is ever dropped.

**Port:**
- `server/quote-workings-screen.ts` — the walk, and the ordered "items" model;
- `server/quote-workings-pdf.ts`.

**Oracle:** this is the "every quote carries its full parameter snapshot, visible on the internal copy" requirement (CLAUDE.md, ERP endgame §10). In Oracle the form layout and the record layout should come from **one definition**, so they can't drift — here they are kept in step by hand.

## 10. Order notes are production instructions

**Data:** 2,638 products carry production notes, e.g.:
- WBIG03: "Smooth side of paper up … CLEAR WASTE REGULARLY", "Speed 9, Heaters 4-4, Plunger 5";
- YF855: "MUST ONLY RUN ON 8RF".

**Oracle:** notes belong to the product, with a type (spec / machine set-up / customer). They should show on quotes and jobs, and on works orders when production is built.
